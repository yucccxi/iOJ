# 文档规范

本规范约定 `docs/` 下文档的目录、命名、结构和写法，不绑定具体语言、框架、数据库、接口协议或部署方式，也不规定具体项目的接口、字段、状态机或实现细节。文中的路径、接口、字段和响应均为示例，实际内容以版本控制中已跟踪的代码、配置和数据定义为准。

> 约定：**必须**表示强制要求；**建议**表示默认这样做，有明确理由时可以例外。

## 1. 目录与职责

### 1.1 目录结构

```text
docs/
├── README.md                 # 文档总索引：所有文档的入口
├── api/
│   ├── README.md             # API 索引 + 通用约定
│   ├── frontend/             # 面向前端 / 外部调用方的 HTTP API
│   └── judge/                # 面向判题机 / 内部调用方的 HTTP API
├── server/                   # 后端技术文档
│   ├── README.md
│   └── ...
└── assets/                   # 文档使用的图片等附件（按需）
```

- `docs/server/` 放关于后端的技术文档。
- `docs/api/` 放 HTTP API 文档，包括面向前端和内部调用方（如判题机）的接口。
- 如果项目没有多个调用方，`frontend/`、`judge/` 等子目录可以不建，直接在 `docs/api/` 下按业务领域拆分。

### 1.2 各目录写什么

| 位置 | 写什么 | 不写什么 |
| --- | --- | --- |
| `docs/README.md` | 文档总索引、阅读路径、维护入口 | 具体接口字段、实现细节 |
| `docs/api/README.md` | API 通用约定：认证、统一响应、分页、错误码、版本策略 | 单个接口的参数与响应 |
| `docs/api/*` | HTTP API 契约，按调用方或业务领域组织 | 内部实现、数据表结构、密钥 |
| `docs/server/` | 架构、数据模型、核心流程、部署、开发、排障 | 重复的 API 字段表 |
| `docs/assets/` | 图片、截图等附件 | 正文文档 |

### 1.3 文档边界

- **API 文档是接口契约**：写 URL、认证、权限、参数、响应、错误码、可见性和副作用。
- **后端技术文档是实现说明**：写为什么这样设计、如何实现、如何部署和排障。
- API 文档不介绍服务端内部实现；后端文档不重复大段接口字段。同一行为如果两处都需要，API 文档作为行为事实来源，后端文档用链接引用。

### 1.4 入口与索引

- `docs/README.md` 必须列出全部文档，并说明每篇的读者和内容。
- 每个文档子目录必须有 `README.md`，作为该目录的索引和阅读顺序；`assets` 目录不需要。
- 每篇文档必须能从至少一个 `README.md` 链接到；不允许存在“孤儿文档”。
- 新增、重命名或删除文档时，必须在同一次修改中更新对应索引和所有引用。
- 根 `README.md` 只保留项目简介、快速开始和文档入口，不复制详细内容。可以加入其它元素（如 TODO List、技术栈的静态徽章等）。

### 1.5 文档依据

- 文档必须以版本控制中已跟踪的项目文件为主要依据，例如源代码、已提交的配置、数据定义、迁移脚本和公开契约。
- 外部标准或官方文档可以作为补充依据，但必须引用稳定、可公开访问的来源。
- 不得把被任意层级 `.gitignore` 规则忽略、未纳入版本控制的文件或目录作为文档依据，包括本地笔记、代理或编辑器工作区、构建产物、依赖目录、缓存、虚拟环境、本地环境变量和凭据文件等。
- 不得在文档中链接、引用或摘录被 `.gitignore` 忽略的内容；这些内容不受版本控制，不能作为稳定、可复现的事实来源。
- 如果某个事实只能从被忽略的文件中获知，必须先把该事实迁移到受版本控制的文件（例如配置模板、示例文件、代码或测试），再基于该文件编写文档。
- `docs/` 目录及其中的文档必须纳入版本控制，不得放在被 `.gitignore` 忽略的路径下。
- `.gitignore` 规则或文件跟踪状态变化后，必须检查文档中是否出现指向未跟踪内容或不再有效的引用。

## 2. 文件与命名

### 2.1 文件名

- 使用小写 ASCII 和连字符：`01-overview.md`、`02-architecture.md`。
- 不允许中文文件名、空格、大写字母；`README.md` 除外。
- 需要表达阅读顺序时使用两位数字前缀：`01-`、`02-`。编号表示顺序，不是稳定标识；插入文档时允许重排编号，但必须同步更新所有链接。
- 一篇文档只讲一个主题；内容过长或读者不同时拆分，不要把所有内容堆进一个文件。
- API 文档按业务领域或调用方拆文件，不按单个接口拆文件；接口在文件内用 `x.y` 编号。
- 图片放在 `docs/assets/<主题>/<名称>.<扩展名>`，文件名同样使用小写英文和连字符，必须使用相对路径引用。
- 禁止提交 `draft.md`、`temp.md`、`新建文档.md` 等临时文件。

## 3. 文档结构

### 3.1 标题

- 每个文件必须有且只有一个一级标题 `#`，标题与文档主题一致。
- 一级标题后先用 1～2 句话说明本文的范围、读者和前置条件。
- 主要章节用 `##`，接口或子主题用 `###`；不要跳级，不要保留空章节。
- 多章节文档使用编号标题，例如 `## 1. 目标与约束`。
- API 接口使用 `### 2.3 创建资源` 这类编号，编号与目录一致。

### 3.2 导航

- 章节文件开头加返回链接：

  ```markdown
  > 返回目录：[API 索引](README.md)
  ```

- 文档末尾可以加 `## 相关文档`，只放确实相关的链接。
- 标题应使用名词短语，不加句号；不要写“关于……的说明”这类冗余标题。
- 修改标题后必须检查跨文件锚点链接是否失效。

## 4. 写作与格式

### 4.1 语言风格

- 默认使用中文；代码、命令、字段名、类名、配置项保留英文。
- 技术术语首次出现时可写“中文（English）”，之后保持同一种叫法。
- 使用陈述句、现在时，直接说明事实和行为；避免“我觉得”“大概”“可能”等模糊表述。确实不确定的行为必须明确标注条件。
- 规范性强弱用词固定：**必须**、**不得**、**建议**、**可以**。
- 一段只讲一个要点，段落尽量短；能用列表或表格表达的内容不要写成大段散文。
- 代码标识符、文件路径、环境变量、枚举值、命令必须用行内代码包裹，例如 `resourceId`、`APP_SECRET`。

### 4.2 结构化表达

- 参数、字段、配置项、错误码用表格，列至少包含“名称、类型/默认值、是否必填、说明”。
- 操作步骤用有序列表；每一步只做一件事，并写明预期结果。
- 枚举值、检查项用无序列表。
- 流程、时序、状态机优先使用 Mermaid；复杂架构图可以使用图片，但必须放在 `docs/assets/` 并提供替代文字。
- 注意事项用引用块，例如 `> **注意**：……`，不要用纯文本“注意！！”。
- 不要用截图代替可复制的文字、命令或代码。

### 4.3 代码块

- 所有代码块必须标注语言：`bash`、`json`、`yaml`、`sql`、`text`、`mermaid` 等。
- shell 命令不要带 `$` 提示符，方便读者直接复制；需要区分普通用户和 root 时，在正文说明。
- 命令必须写明工作目录，例如“以下命令在仓库根目录执行”。
- 示例 JSON 必须是合法 JSON，不能带注释；使用假 id、假用户名和 `<placeholder>` 形式的密钥。
- 必须展示 `null`、空数组 `[]`、空对象 `{}` 等边界值，不能只给理想数据。
- 不要粘贴大段源码；需要引用实现时，链接到具体文件或类，并说明关键行为。

### 4.4 表格、时间和单位

- 表格必须有表头和分隔行，列数保持一致；避免合并单元格。
- 表格单元格内容过长时，把补充说明放到表格下方，不要硬塞进单元格。
- 时间格式在 API 通用约定或项目约定中统一规定；文档使用该格式，并注明是否带时区。
- 耗时、内存、文件大小等单位在同一文档内必须统一，并在首次出现时说明。
- 数字与单位之间加空格（如 `300 ms`、`256 MB`），代码标识符除外。

### 4.5 链接与安全

- 仓库内链接使用相对路径，只能指向版本控制中已跟踪的文件；不要链接被 `.gitignore` 忽略的路径。
- 不要使用作者机器上的绝对路径。
- 外部链接必须指向稳定的官方文档；不要链接搜索结果页或临时地址。
- 文档中不得出现真实密码、令牌、密钥、连接凭据、用户邮箱或个人信息；凭据统一使用 `<token>`、`<secret>`、`<password>` 等占位符，邮箱等示例数据使用保留域名。
- 默认账号或初始密码只能作为首次启动示例出现，必须同时提示“首次使用后立即修改”。
- 破坏性命令（删除数据、清空目录、重建数据库）必须明确标注影响范围。

## 5. API 文档规范

### 5.1 文件划分

`docs/api/README.md` 放所有接口共用的约定；具体接口按调用方或业务领域拆分。调用方较多时可以建子目录，例如 `frontend/`、`judge/`。

- 同一个接口只能在一个文件中定义，其他文档用链接引用。
- 每个领域文件开头说明该文件覆盖的资源、读者和通用前置条件。
- 内部调用方的接口必须与面向用户的接口分开，并明确标注不是公开接口。

### 5.2 单个接口必须写清楚

每个接口至少包含以下内容：

1. **方法和完整路径**：例如 `POST /api/...`，包含路径参数和版本前缀。
2. **权限和可见性**：公开、登录用户、资源所有者、管理员或内部调用方；不同身份返回字段不同时，用表格列出差异。
3. **请求**：路径参数、查询参数、请求头和请求体分别列表，写清类型、是否必填、默认值、取值范围和含义；枚举字段链接到枚举说明。
4. **成功响应**：给出业务数据的 JSON 示例和字段表；说明可能为 `null`、空数组或空对象的情况。
5. **失败情况**：列出 HTTP 状态码、业务错误码和触发条件；只写该接口真实会返回的错误，通用错误链接到统一错误码表。
6. **行为说明**：同步还是异步、是否有副作用、是否幂等、限流规则、重试建议、排序规则和超时行为。
7. **示例**：至少一个请求示例和一个响应示例；不同角色看到的字段不同时，给出多个响应示例。

补充要求：

- 列表接口必须写明排序字段和方向、筛选条件之间的关系、默认页大小和最大页大小。
- 创建、修改接口必须写明冲突行为、是否返回完整资源、重复提交的后果。
- 删除接口必须写明关联数据如何处理（级联删除、软删除或保留）。
- 登录相关接口必须写明令牌有效期和失效条件。
- 文件上传、下载接口必须写明 `Content-Type`、大小限制、编码和失败时的响应格式。
- 字段名必须与接口定义或数据模型完全一致；不要使用调用方自造的名称。
- 明确区分“字段不返回”“字段为 `null`”和“字段为空数组/空对象”。

### 5.3 通用约定

`docs/api/README.md` 必须集中维护以下内容，其他文档引用而不是重复：

- Base URL、版本前缀和请求格式。
- 认证方式：不同调用方使用什么凭据、放在哪个请求头、如何失效；不同凭据不得混用。
- 统一响应结构、成功判定方式和错误信息字段。
- 分页参数、默认值、上限和越界行为。
- 时间、枚举大小写、字段命名等通用格式。
- 错误码总表：业务错误码、HTTP 状态、含义、调用方处理建议。
- 版本策略和兼容性说明。
- 跨域、限流、幂等等跨接口约定（如果存在）。

具体前缀、默认值、状态码和错误码以版本控制中已跟踪的代码和配置为准；文档只维护一份权威说明，不在多个文件中重复。

### 5.4 内部或机器调用 API 的额外要求

面向内部服务、判题机或其他机器调用方的接口，文档中必须醒目标注：

> **内部接口**：仅供内部调用方使用，不得暴露到公网或写进公开调用示例。

还必须写清楚：

- 认证方式与用户接口的区别，以及凭据的获取、轮换和失效方式。
- 协议版本的含义、当前版本和兼容策略；协议变更时同步更新文档。
- 任务或资源的生命周期、状态机和异常分支。
- 并发、幂等、重试、过期和重复请求的处理方式。
- 非 JSON 响应（如二进制、流式响应）的格式、响应头和失败时的表现形式。
- 启动引导、配置校验或健康检查失败时的行为。
- 超时、重试、退避和时钟偏差的处理建议。

建议用 Mermaid 时序图展示一次完整调用流程，并在图下方用文字说明异常分支。

## 6. 后端技术文档规范

### 6.1 主题划分

`docs/server/` 建议覆盖以下主题，具体篇目和命名按项目实际确定，并在 `docs/server/README.md` 中建立索引：

| 主题 | 内容 |
| --- | --- |
| 总览 | 技术栈、代码结构、快速开始、配置项、测试、常见问题 |
| 架构 | 目标与约束、模块边界、请求链路、核心流程、权限模型、关键取舍 |
| 数据模型 | ER 图、表/字段/类型/索引、枚举、容量估算、初始化、迁移、备份 |
| 核心流程 | 状态机、异常分支、限额、错误映射、安全要求 |
| 部署与运维 | 环境要求、初始化、配置、进程管理、反向代理、备份恢复、升级回滚、检查清单 |
| 开发指南 | 分层规范、扩展步骤、测试、踩坑记录 |
| 排障 | 常见现象、原因、处理步骤和验证方法 |

### 6.2 每篇技术文档的要求

- 开头说明范围、读者和前置条件。
- 涉及操作时给出可复制命令、工作目录和预期结果。
- 涉及配置时使用表格：变量名、是否必填、默认值、作用、安全注意事项。
- 配置项只能有一份权威表格；其他文档用链接引用，避免默认值改了两处不一致。
- 数据模型文档以项目实际的数据定义和迁移脚本为准；结构变更必须同步更新图表、字段说明和索引说明。
- 架构文档要解释“为什么这样设计”，包括约束、备选方案和取舍，不能只画图。
- 核心流程文档要写清状态机、异常分支、限额和错误映射，不能只写正常流程。
- 部署文档按“准备 → 初始化 → 配置 → 启动 → 验证 → 备份/回滚”的顺序组织，每一步都有验证方法。
- 排障内容使用“现象 → 原因 → 处理 → 验证”的结构，尽量给出日志关键字。
- 版本号以项目依赖清单或配置文件为准；文档只写最低要求或引用文件，避免硬编码易过期的补丁版本。
- 命令中不要出现作者的个人绝对路径、私有 IP 或真实域名；使用 `<host>`、`<server-url>` 等占位符。
- 不要复制整段源码；用类名、文件路径和关键代码片段说明实现。

## 7. 维护与评审

### 7.1 同步规则

文档是变更的一部分。以下改动必须在同一次提交或同一个 PR 中更新对应文档：

| 变更 | 必须更新 |
| --- | --- |
| 新增、修改、删除 HTTP 接口 | 对应的 API 文档；必要时更新通用约定和索引 |
| 字段、枚举、错误码、权限变化 | 对应 API 文档、错误码总表和示例 |
| 数据模型、索引、迁移脚本 | 数据模型文档和迁移说明 |
| 配置项、默认值、环境变量 | 配置说明和部署文档 |
| 核心流程、状态机、协议变化 | 核心流程文档和相关 API 文档 |
| 部署方式、依赖、端口变化 | 部署文档和根 README 的快速开始 |
| 架构或模块边界变化 | 架构文档和开发指南 |

补充规则：

- 接口行为有变化时，先确定新的契约并更新 API 文档，再改实现；至少不能出现代码已合并、文档仍描述旧行为的情况。
- 代码与文档冲突时，以版本控制中已跟踪的代码、配置或数据定义为准，并在当前变更中修正文档；不允许长期保留两套说法。
- 废弃接口或配置必须标注“已废弃”、替代方案和移除计划；不要直接删除读者仍可能依赖的说明。
- `.gitignore` 规则或文件跟踪状态变化后，必须检查文档中是否引用了不再受版本控制的内容。
- 文档迁移或重命名后，必须检查所有相对链接和锚点。

### 7.2 评审清单

提交文档或包含文档的代码变更前，逐项确认：

- [ ] 文档开头说明了范围、读者和前置条件。
- [ ] 标题层级正确，一个文件只有一个一级标题，没有空章节。
- [ ] 接口字段名、类型、默认值、权限和错误码与代码一致。
- [ ] 成功、失败、`null`、空数组、分页和异步行为都有说明。
- [ ] 示例 JSON 合法，命令可复制，敏感信息已替换为占位符。
- [ ] 表格、代码块、Mermaid 图表能正常渲染。
- [ ] 文档依据和链接均来自版本控制中已跟踪的文件，没有引用被 `.gitignore` 忽略的内容。
- [ ] 相对链接和锚点有效，新文档已加入索引。
- [ ] 没有重复维护的权威表格或互相矛盾的说法。
- [ ] 中文表述清晰，术语前后一致，没有营销式空话。
